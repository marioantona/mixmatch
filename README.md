# MixMatch

**The fastest way for a group of friends to decide where to go out tonight.**

Everyone in the group swipes on the same deck of nearby bars, pubs and clubs. When the
whole group swipes right on the same venue, it's a match, and the app gives you walking directions.
Ratings are weighted towards reviewers with taste like yours. The quick tags reviewers tap
gradually become tags on the venue itself.

> Mobile-first web app (Next.js + Supabase), built in **3 hours** at a University of
> Manchester hackathon in September 2026. Seeded with real Manchester city-centre venues from OpenStreetMap.

## The problem

Choosing where to go turns into forty messages in the group chat, and you still end up in the
same pub. With hundreds of venues in a city centre and everyone on a different budget, it's hard
to find somewhere that suits the whole group, or to discover anywhere new.

## Features

- **Onboarding in three taps:** name, budget (£ / ££ / £££), at least three vibes (DJ sets, real ale,
  karaoke, beer garden…), and an "I'm 18 or over" confirmation. No account needed.
- **Discover:** a swipe deck of nearby venues ranked for you. Swipe right for "I'm in" and left to pass.
  There are also ✕ / ✓ buttons and ← / → keys on desktop. A filter sheet covers budget,
  distance and vibes, and you can switch to **map** or **list** view of the same ranked results.
- **Liked:** the venues you said "I'm in" to, with personal scores, and an option to remove them.
- **Groups:** start a group to get a 4-letter code and a share link (`/g/CODE`), or join with a code.
  Everyone swipes the **same deck in the same order**. When every member has liked a venue,
  a full-screen **match reveal** plays on all phones in real time. Members can leave the group, and
  their departure updates live.
- **Venue detail:** tags (tags added by reviewers are highlighted), a personal rating line
  ("People like you: 86% thumbs up · 12 similar reviewers"), an estimated pint price, a map pin, a walking-directions
  link and recent reviews.
- **Rate your night:** thumbs up/down, one-tap tag chips and an optional comment.
- Installable as a home-screen web app (manifest + generated icons).

## How it works

### Taste vectors
[`src/lib/tags.ts`](src/lib/tags.ts) defines a fixed vocabulary of 20 tags (music, vibe, drinks,
crowd, price). Their order defines the dimensions of every vector:

- A **user's taste** starts from their onboarding vibes and budget (`tasteFromOnboarding`). Every swipe
  nudges it towards a liked venue or away from a passed one (`updateTaste`, learning rate 0.15 for a like
  and 0.08 for a pass), then re-normalises it.
- A **venue's vector** combines its tags, a partial contribution from review mentions, and its price level
  (`venueVector`).

### Ratings from people like you
Instead of a global average, `personalRating` weights each review by how similar the reviewer's taste
is to yours, then shrinks the result towards a prior so a venue with few similar reviewers doesn't
swing to 0% or 100%:

```
score = (Σ wᵥ·yᵥ + k·prior) / (Σ wᵥ + k)      wᵥ = max(0, cos(you, reviewerᵥ))²,  prior = 0.65, k = 2
```

### Reviews tag venues automatically
A tag that **3 or more different reviewers** tap on a venue becomes a public tag on it
(`effectiveTags`, backed by the `venue_review_tags` SQL view) and is marked "added by reviewers".
This tagging uses no LLM; it is plain consensus counting.

### Ranking
`rankVenues` filters by budget, distance and vibes, then scores each venue as

```
0.55 × taste match (cosine)  +  0.30 × personal rating  +  0.15 × proximity
```

About every fifth card is an **exploration pick** from the lower half of the ranking, labelled
"Something different", so the deck doesn't become a filter bubble. The picks are deterministic,
so every run of the demo looks the same.

### Group matching
- The group deck is ranked with the **normalised average of members' tastes** (`groupTaste` in
  [`src/lib/group.ts`](src/lib/group.ts)). Every phone uses identical inputs (members sorted by id and a
  shared origin, with no exploration picks), so every member sees the same order. Group swipes
  don't change anyone's personal taste.
- Each swipe is saved with the group id. Clients subscribe to `swipes` changes for their group via
  Supabase Realtime, with a 5-second poll as a fallback for flaky Wi-Fi. On each change they call the
  `group_matches` Postgres function, which returns the venues every current member has liked.
- Leaving a group deletes that member's group swipes first, so the person who left can't block future matches.

### Data
- **Real:** venue names, locations, types and addresses come from OpenStreetMap (Overpass API),
  covering 1.6 km around Piccadilly Gardens. A few tags come from OSM too (live music, real ale, beer
  garden, LGBTQ+). The data is cached in `scripts/osm-venues.json`, so the seed never depends on Overpass.
- **Simulated:** price levels, pint prices, most vibe tags, and all seeded reviewers and reviews.
  70 synthetic reviewers across 7 taste "archetypes" each visit about 30 venues, with reviews biased by
  taste similarity. The seed is deterministic, and the app never presents this data as verified.
- Crowd tags such as `lgbtq_friendly` describe venues, never users. They are only taken from real OSM
  data, never simulated. The app doesn't ask for or infer any protected characteristics.

## Running it locally

Prerequisites: Node.js 20+ and a free [Supabase](https://supabase.com) project.

```bash
git clone https://github.com/marioantona/mixmatch.git
cd mixmatch
npm install
```

1. **Database:** in the Supabase dashboard, open **SQL Editor**, paste the whole of
   [`supabase/migrations/0001_init.sql`](supabase/migrations/0001_init.sql) and run it. This creates the
   tables, views, the `group_matches` function and the Realtime publication. It is safe to re-run, but
   re-running wipes the data.
2. **Environment:**
   ```bash
   cp .env.example .env.local
   ```
   Fill in the project URL and the publishable (anon) key from **Project Settings → API**, plus the
   secret (service role) key. Only the seed script uses the secret key, so never expose it to the browser
   or add it to Vercel. Change `NEXT_PUBLIC_DEMO_LAT/LNG` to seed a different city.
3. **Seed venues and reviewers:**
   ```bash
   npm run seed              # uses the cached OSM data
   npm run seed -- --refresh # re-fetches venues from OpenStreetMap
   ```
4. **Run:**
   ```bash
   npm run dev
   ```
   Open <http://localhost:3000/?demo=1>. `?demo=1` pins your location to the seeded city centre;
   without it, the app tries geolocation and falls back silently. To try groups on one machine, use
   two browser profiles (or a private window): create a group in one and join it from the other.

Other commands: `npm run build`, `npm run lint`, `npx tsc --noEmit`.
[`supabase/reset-demo.sql`](supabase/reset-demo.sql) removes every real user, group, swipe and review
while keeping venues and synthetic reviewers. It's useful before a live demo, and irreversible.

To deploy, import the repo into Vercel and set `NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_DEMO_LAT` and `NEXT_PUBLIC_DEMO_LNG`. Geolocation needs HTTPS,
so test on phones through the deployed URL.

## Limitations

This is a 3-hour prototype, and the shortcuts are deliberate:

- **No real authentication or security.** A profile is a UUID generated on the device and kept in
  `localStorage`, and the database's row-level security policies are wide open. Anyone with the public
  anon key can read and write every table, including impersonating another profile. Clearing browser
  storage loses your profile.
- **Most venue data is simulated.** Prices, most tags and all seeded reviews are generated, so the
  recommendations show how the method works rather than reflecting the real venues.
- **Stale and incomplete venue data.** OpenStreetMap can list venues that have closed. Opening hours
  are ignored, so the app may suggest somewhere that's shut tonight.
- **Simple recommendation model.** It's a linear taste vector over a fixed hand-written tag vocabulary,
  with no collaborative filtering beyond reviewer similarity. New users and new venues face a cold start.
- **Strict group rule.** A match needs *every* member to like a venue. Large or picky groups may never match.
- **One city.** Venues are seeded around a single point (central Manchester). Outside that area, the app
  falls back to the demo location.
- **No moderation** of review text, and no rate limiting.
- **No automated tests or CI.** Checks were type-checking, linting, builds and manual testing on phones.
- Code quality is uneven in places, as you'd expect from AI-generated code written against a deadline.

## Where it could go next

- **Accounts and real security:** Supabase Auth, row-level security scoped to the user and group members,
  and a profile that syncs across devices.
- **Real venue data:** opening hours, venue-verified prices and events, and partnerships with venues, which
  is a natural business model for a city whose nightlife needs footfall.
- **Smarter tagging and ranking:** extract tags from free-text reviews with an LLM, learn embeddings
  instead of a fixed vocabulary, and add time-of-night and day-of-week context.
- **Better group decisions:** majority or ranked-choice matching, a time limit ("decide in 5 minutes"),
  and push notifications when the group matches.
- **More of a product:** photos, a venue dashboard, more cities, and a native app.
- **Engineering:** unit tests for `scoring.ts`, end-to-end tests for the group flow, CI on pull requests,
  and proper database migrations.
